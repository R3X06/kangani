# Kangani evaluation harness

Measured evidence about how the agent behaves, separated from claims about how
well it works.

Numbers live in [`METRICS.md`](METRICS.md), which is generated by
`report.py` and never edited. This file restates none of them on purpose: a
hand-copied figure goes stale the first time the suite re-runs, and a stale
number is worse than a missing one because it still reads as authoritative.
Charts are in [`analysis.ipynb`](analysis.ipynb) and `figures/`.

## Two datasets, never blended

**A — synthetic.** A prompt suite executed against seeded fixtures. Every
prompt was written to reach a specific branch, so A can say what is
*reachable*, how often dispatch picks the intended tool, and whether the
deterministic router ever fires when it shouldn't. It cannot say anything about
quality of use. A tool's frequency in A is a fact about how I wrote the suite.

**B — real.** Instrumented turns from the running bot, and correctness claims
only on the subset labelled by hand. B is the only dataset that can support a
statement about whether an answer was right.

Sample sizes are reported separately in `METRICS.md` and never summed. Every
table and chart title carries an `[A]` or `[B]` prefix. Where B is absent, the
relevant section prints why rather than filling in from A.

## Layout

```
eval/
  seed.py          deterministic fixture generator, four DB states
  prompts.yaml     85 prompts: 31 tool, 32 route, 6 normalization,
                   10 near-miss, 6 state-specific
  run.py           executes the suite, caches raw API responses
  analysis.ipynb   pandas / numpy / matplotlib / sklearn
  report.py        generates METRICS.md from run artifacts
  db/              fixtures (gitignored)
  cache/           raw API responses (gitignored)
  runs/            results.jsonl + manifest.json per run (gitignored)
  real/            copy of the production DB for dataset B (gitignored)
  figures/         charts
```

## Running it

```bash
python eval/seed.py --state full        --out eval/db/full.db
python eval/seed.py --state empty       --out eval/db/empty.db
python eval/seed.py --state single      --out eval/db/single.db
python eval/seed.py --state conflicting --out eval/db/conflicting.db

python eval/run.py --state full --repeats 5
python eval/run.py --state full --repeats 5 --ceiling
python eval/run.py --state empty --repeats 3
python eval/run.py --state single --repeats 3
python eval/run.py --state conflicting --repeats 3

python eval/report.py          # -> METRICS.md
# then run analysis.ipynb
```

Re-running analysis costs nothing. `run.py --replay` refuses to make a live
call and serves entirely from `cache/`.

## What makes the numbers trustworthy

**Fixtures restore before every execution.** 21 of the 31 tools mutate state.
Restoring per suite instead of per execution would mean repeat 2 runs against
whatever repeat 1 left behind, and the "dispatch variance" measured would be
partly fixture drift.

**The response cache is keyed on the repeat index.** Keying on the request
payload alone is self-defeating: repeats 2–5 are byte-identical requests, so
they would all hit repeat 1's entry and variance would read as exactly zero.

**Provenance is recorded per run.** Each `manifest.json` carries the model, the
*effective* `MAX_TOOL_ITERATIONS`, cache hit/miss counts, and the SHA-256 of
the fixture. Every figure traces to one run directory.

**Effective values, not requested ones.** See failure mode 2.

# Failure modes

Three found while building the harness, plus one property of the retrieval
layer that is a design limit rather than a defect. All four are about the
system under test or the measurement of it. Agent-behaviour failure modes
require dataset B and are not guessed at here.

## 1. The system prompt leaked the wall clock into every request

First replay run returned **zero** cache hits. Not one.

The cache key is a hash of the request payload. `build_system_blocks` embeds
the current local and UTC datetime — that's deliberate and correct in
production, since the agent has to resolve "tomorrow" against something. But it
means no two requests are ever byte-identical, so the cache could never hit and
`--replay` was structurally impossible.

The cache was the smaller half. The fixture anchors semester week 1 to a fixed
Monday and derives every deadline from it, precisely so date-relative prompts
mean the same thing on every run. Meanwhile the agent was being told the real
date. Run the suite on the 1st and "what's due this week" resolves against one
calendar; run it on the 8th and it resolves against another, while the fixture
hasn't moved. Results would have drifted a little further every day and nothing
would have looked broken — the prompts still run, the tools still fire, the
answers are still fluent.

Root cause: reproducibility was treated as a property of the fixture generator,
when it is a property of everything the agent reads. The fixture was pinned;
the clock the agent was shown was not.

Fix: `run.py` patches `datetime.now()` in `brain` and `tools` to the fixture's
own `FIXTURE_NOW`. After that, replay reproduced a live run exactly, including
the per-repeat variance.

Still open, and stated in the code: SQL-side `STRFTIME('now')` is untouched.
`seed.py` canonicalizes column defaults, but a query that *filters* on `'now'`
— `get_pending_future_reminders` — still sees the real clock. Any metric
resting on that comparison is not frozen.

## 2. The ceiling run silently ran at the default ceiling

`--ceiling` reported a 0% ceiling-hit rate. The obvious reading is that the
synthesis-on-ceiling path is hard to reach. The actual reading is that the
ceiling was never lowered.

`MAX_TOOL_ITERATIONS` is a module-level constant read once at import.
`run.py` sets `KANGANI_MAX_TOOL_ITERATIONS` inside `run()`. In normal CLI use
that ordering is fine — nothing has imported `brain` yet. Import `brain` first
for any reason and the environment variable arrives after the constant is
already bound, and the run executes at 10 while its filename, its output
directory, and its own logs all say it is testing 2.

What makes this worth writing down is that it is a *measurement* bug that
produces a plausible *finding*. A 0% ceiling rate is publishable-looking. There
is no error, no traceback, nothing anomalous in the results — just a number
that means something other than what it appears to.

It was caught because `manifest.json` records the effective value rather than
the requested one. That was defensive habit, not foresight, and it is the only
reason the run was distinguishable from a real result.

Fix: set the module attribute directly and warn if the effective value
disagrees with the run's intent. Under the corrected config the ceiling path is
comfortably reachable — see `METRICS.md`.

## 3. A seeded RNG did not make the fixtures reproducible

`seed.py` uses one fixed seed and no wall-clock reads. Building the same state
twice still produced different files.

Two sources. `created_at` and its variously-named siblings default to
`STRFTIME(...,'now')` in the schema, and `_new_tag` mints reference tags with
`secrets.token_hex`, which is deliberately unseedable.

Neither is cosmetic. Tags are printed in tool output as user-facing handles, so
the agent literally sees different text between runs. And `query_notes` orders
by `created_at DESC` — rows written in the same millisecond come back in an
unstable order, so the agent receives its notes in a different sequence run to
run, for reasons entirely unrelated to the model.

The fix took three attempts, and the first two are the interesting part. A
hand-written list of timestamp columns missed `files.uploaded_at`, then missed
`tasks.updated_at`. Four different names across seven tables — `created_at`,
`updated_at`, `uploaded_at`, `timestamp`. The third attempt discovers them from
`PRAGMA table_info` by looking for defaults containing `STRFTIME`, which is
exact and does not go stale when a column is added later.

Root cause is the same shape as failure mode 1: determinism was assumed to be a
property of the generator's own code, when it is a property of every write path
the generator touches.

## 4. BM25 cannot see a paraphrase, and the fixture proves it

Not a defect — a lexical index doing exactly what a lexical index does — but it
bounds what the retrieval layer can claim.

The fixture plants three near-duplicate pairs. Each states the same fact twice:
once sharing the query's vocabulary, once paraphrased with almost no shared
terms. *"Backpropagation applies the chain rule to compute the gradient"* and
*"Computing derivatives of a composed function by working backward from the
output"* mean the same thing and share nearly no words.

Results are in `METRICS.md`. The useful part is that the failure is **graded,
not binary**: two pairs lose the paraphrase entirely, while the third retrieves
it at a small fraction of the lexical member's score, because that pair happens
to share a couple of incidental terms. The gap tracks lexical overlap rather
than switching on and off.

This is the evidence for or against adding a semantic arm. The original plan
called for BM25, cosine over embeddings, and Reciprocal Rank Fusion. Only BM25
is built; cosine needs an embedding source, which means either a second API
provider on the note-write path or a local model heavy enough to be a problem
in a container that already carries Chromium. That decision was deferred to
real usage rather than argued in the abstract.

Until it is made, the retrieval section reports one ranking and says so. A
fusion table assembled from a ranker that does not exist would be precisely the
kind of number this harness exists to prevent.

# Known gaps

**Dataset B is young.** Instrumentation shipped recently; real turns accumulate
only while the bot runs. The failure regression will not fit below 40 labelled
rows and prints why instead of producing coefficients with error bars wide
enough to include zero in both directions.

**"Failure" needs hand-labelling.** `is_error` from `execute_tool` is free but
only catches a handler raising, and most of what it flags is a bad id the model
recovers from on the next round. It cannot see the failure this project most
wants to catch — the one recorded in `brain.py`'s own `_commit` docstring,
where Kangani confidently reported reminders that were never created. Every
tool returned clean. No fallback string fired. `is_error` was zero. It is
visible only by reading the reply, which is why `turns` captures `user_text`
and `reply_text` from day one. Label into `correct` / `soft_wrong` /
`hard_fail`; `soft_wrong` is the class worth predicting.

**`progress_logs` is a dead table.** It is in the schema, is migrated, counted
and cascaded, and nothing in the codebase has ever written to it. There is no
create function and no tool that reaches it — `seed.py` populates it with raw
SQL for that reason. It is the table-level version of the dead-tool question
the analysis asks one level up.

**Inline button callbacks are not instrumented.** Only text turns are.
Button-route share therefore means "share of inbound text messages that never
reached Claude", not "share of all interactions". Tapping an inline keyboard
under a message is a different surface and is out of scope.

**Synthetic tool frequency is not usage.** Worth repeating because the coverage
chart invites the misreading. The suite contains one prompt per tool by
construction. Frequency there describes the suite.
